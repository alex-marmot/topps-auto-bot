# 付款、本人验证与结果核对

## 本地明文配置

信用卡资料按用户选择保存在当前用户数据目录的 `config.json` 中，属于**本地明文**，不是加密存储。程序不会把卡资料、地址、Cookie、令牌或带会话参数的结算 URL 写入 `run-state.json`、日志或诊断。请保护 Windows 账户和配置文件。

## 自动付款边界

- 只有来源可信、完整订单核对通过、配送快照一致且本地提交记录已成功保存时，才允许发起一次最终购买提交。
- 提交前必须再次检查停止信号和当前安全前提；没有整单截止。记录保存失败则不点击。
- 每个任务最多尝试一次最终购买提交。异常、超时、重复事件、刷新或关闭页面都不会触发 JavaScript 补点、另一种点击方式或重新提交。
- 银行验证由本人在专用 Chrome 中完成。它与订单结果共用从付款动作发出起的 10 分钟，程序只核对结果。到期未能确认时保留未决记录。

## 加购与付款提交记录

`run-state.json` 使用 schema 2，可包含加购尝试历史、当前加购记录和购买提交记录。记录只包含：任务标识、状态、尝试序号、流程类型、唯一目标、数量、实际提交/更新时间、金额、配送服务和运费快照、订单/付款结果；不包含卡资料、地址、Cookie 或令牌。旧 schema 1 的购买记录仍按旧流程读取并阻断。

以下状态会阻止新任务：

- 加购 `IN_FLIGHT` / `UNKNOWN`：加购可能已发出，但购物车结果未确认。
- 付款 `SUBMITTING` / `UNKNOWN`：购买提交可能已发出，但没有足够证据确认订单/付款结果。
- 文件损坏、不可读或版本不支持：保留原记录，按未决阻断处理。

停止程序、异常退出、覆盖升级、重启、购物车变空或再次点击开始都**不能**自动解除阻断。一次空车读数也不能证明旧加购没有发生。

## 出现未决记录时

### 未决加购

1. 先不要重复点击官网加购按钮，也不要删除或覆盖 `run-state.json`。
2. 打开官方购物车，确认目标商品、规格和数量是否已存在；必要时检查订单历史。
3. 在“未决加购与付款核对”中显式记录：
   - 已成功（购物车确有该目标）
   - 明确失败（确认没有新增条目）
   - 未形成加购
4. 程序解除加购阻断。旧任务结束；新任务仍必须先从空购物车开始，不能接续疑似旧加购的购物车付款。

### 未决付款

1. 使用“打开官网订单页面”，登录官方账户查看订单历史和支付状态；必要时在支付渠道核对。
2. 确认结果后显式选择成功、拒绝/失败或未形成订单。
3. 程序记录结论并解除付款阻断。旧任务保持结束，**不会**自动恢复或重新提交旧付款；新任务必须重新准备并重新通过全部检查。

如果记录文件损坏或无法读取，程序保留原文件并继续阻断。此时先保留现场并核对官方页面；不要用空状态覆盖原文件。

## 报告结果的含义

- **订单已确认**：能关联到本次唯一目标，取得订单标识，且付款明确接受。
- **失败/拒绝**：官网明确拒绝付款；不自动重试或换卡。
- **结果不明**：加载中、空白页、无订单标识、订单不匹配、付款未明确接受或结果相互矛盾。必须人工核对。
- **未提交**：停止或记录后的安全检查失败发生在实际点击前，且当前进程能证明没有发出动作。

购物车存在、加购成功、进入结算、按钮消失、点击返回或固定时间流逝都不能作为订单成功证据。客户端单次点击不能为第三方支付提供服务端幂等保证。
