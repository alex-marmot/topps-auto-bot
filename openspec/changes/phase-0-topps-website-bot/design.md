# Design

## Context

动机与交付范围见 [proposal.md](proposal.md)。已有 UC、自动登录和完整下单基础及 209 项历史测试记录，但全局 verified 阻断、真实支付 iframe 和审查发现的重试/超时缺口仍需处理。本轮仅改规范：交付可安装且流程完整的试用版本，用户人工登录、配置卡和收货资料后开始；开发者真实登录/付款证明不再是启动或交付前置。真实试用记录与开发验收分别报告。

此前只读审查过参考项目提交 `7a123e13241167d4e92d66ff03a17205363c996e` 的六个文件，其中 `main.py` 为 834 行，`BACKUP.PY` 为 604 行；未安装依赖或运行。这些观察只用于功能研究和错误案例背景，不作为源代码、注释、文档、资源或实现结构的移植模板。新实现以本项目规格、官方库文档和独立核实的网页行为为依据。已有源码阅读事实也意味着本项目不宣称严格净室开发。研究记录如下：

| 观察 | 参考项目位置 | 对设计的约束 |
| --- | --- | --- |
| 配置、浏览器、线程和 UI 集中在一个文件 | `main.py:365-834` | 只按职责做必要拆分，不做通用框架 |
| UC、持久化 profile、AutomationControlled 配置及固定 Chrome 146 | `main.py:21-38` | 保留参考浏览器兼容方案，动态匹配版本；no-sandbox 单独诊断并记录实际参数 |

2026-11-06 的隔离浏览器只读调查可打开官网首页，已正常加载的公开脚本中能看到购物车 Server Actions 与结算跳转；实际 `getCartAction` 的 `POST /` 和购物车页面曾返回 403，购物车页面显示 Cloudflare 拦截。本次未登录、未加购或付款，最终订单/信用卡提交接口未验证。观察到动作名不代表存在可直接重放的公开 API，也不能仅凭 403 推断缺少 CSRF token。

参考版本的实际步骤为：启动浏览器和首页、按需要提示人工登录、直链或关键词定位商品、设置数量、点击加购、进入购物车并结算、填收货资料与信用卡、点击付款。它还含有库存等待和搜索结果逐个购买分支，但没有定时启动、有限提交窗口或性能指标；点击后等待五秒即报成功也不是可靠的成交证据。新基线复现业务顺序，仍遵守此前确定的单目标、精确数量、预算、独立步骤超时及防重复付款规则。

优先用参考浏览器启动基线核实首页/商品页可访问，再核实规格/数量控件、加购结果、登录要求、结算表单及付款动作语义，不要求官网允许开售前加车或预填。用户已提供过测试入口，现有访问记录为 Cloudflare 403；详见 docs/validation.md，尚不能证明真实流程可用。

## Goals / Non-Goals

**Goals:**
- 先跑通参考项目从商品页到付款结果的完整顺序，可用普通在售直购商品建立基线，再根据实际失败步骤和耗时决定抢购改良。
- 让界面、配置与执行各自可验证，同时保留用户决定的 Tkinter、信用卡自动付款和本地卡资料保存。
- 把唯一购买目标、完整数量、美元预算、购物车一致性及付款次数控制变成执行路径上的强制检查。
- 让普通 Windows 用户通过安装向导和设置窗口完成准备、取消下载或手选驱动，无需编辑 JSON。
- 用代码、受控测试和 Windows 安装/升级验收证明可交付；真实账号登录和付款由用户自愿试用，单独记录，不成为全局运行或归档前置。

**Non-Goals:**
- 不实现网站后端、多个账户并发、平台抽象层、手机控制或其他网站。
- 不自动完成验证码或银行验证，不伪造登录授权；保留参考的浏览器自动化识别兼容方案，但不将参数配置当成 Cloudflare 已通过的证据。
- 基线不实现自动删车/补量、独立 HTTP 下单或内部 Action 重放、抽签/拍卖、多目标合并、支付失败重试、云同步或替换 UI 技术栈。定时抢购、预备车/结算页加速及 P95≤500ms 门槛延期到基线评价后另行修订，不阻塞完整流程测试。

## Decisions

### 1. Runtime and delivery baseline

- 技术路线固定为 CPython、Tkinter/ttk、Selenium + undetected-chromedriver 和用户安装的 Chrome。当前开发环境为 CPython 3.14.x；新增 UC 后先验证 Python、Tk、Selenium、UC、Chrome 和 Windows 打包的实际兼容性，再把实际使用的补丁版本及依赖锁定。文档不把本机已有版本当作 Windows 已验证版本。
- 源码保留跨平台路径处理，第一交付和验收目标为 Windows 10/11 x64；macOS 可做开发验证，但不能代替 Windows 安装验收。
- 使用 Python 标准库处理 JSON、Decimal、路径、下载、队列及日志；必要测试工具为 pytest。暂不新增数据库、Web 服务、UI 组件框架。
- 用户安装产物使用 PyInstaller `onedir` 收集 Python/Tk 运行时，再以 Inno Setup 生成用户级 Windows 安装程序。其准确版本和发布许可在构建时记录。选择 `onedir` 是为减少每次解包和资源路径差异，安装器负责对普通用户隐藏内部文件。
- 浏览器基线采用 UC + 可见 Chrome + 专用持久化 profile，保留 `--disable-blink-features=AutomationControlled`。参考的 `--start-maximized`、`page_load_strategy='normal'`、`use_subprocess=True` 作为启动对照组合；`--disable-dev-shm-usage` 按平台核实。普通 Selenium 仅用于比较诊断，不默认替换用户要求的方案。当前 156 是已有本机记录，不硬编码 146 或 156；每次准备检测实际浏览器版本并验证匹配。
- `--no-sandbox` 是独立的显式诊断兼容选项，默认保留沙箱；UC 当前构造参数默认 `no_sandbox=True`，实现须显式覆盖并检查最终启动参数。参考原组合可作为诊断对照，但不能因 403 就无条件关闭沙箱，不能宣称该参数等于反检测。每组试验记录 Chrome/驱动/UC 版本、最终参数、profile 类型、页面状态及结果，不采集凭据。
- 诊断入口允许查看首页或商品页，不要求先填信用卡或登录密码，也不要求先取得开发者实站通过记录；正常浏览器会话可由用户人工完成站点挑战。空白浏览器可启动、首页 HTTP 200、登录成功、商品可操作、付款成功是不同证据。持续 403/挑战时标记该实站步骤未通过，保留现场，不继续填卡或声称只是选择器问题。
- 第 0 阶段不要求预先取得代码签名证书，可先构建并验收未签名的 Windows 安装包，记录签名状态及实际系统提示。以后若需要签名分发，再另行准备证书；不得把签名状态不明确写成已签名或要求用户关闭系统保护。

### 2. Minimal module boundaries

以下模块及测试目录已经建立；职责说明是新流程适配目标，不表示自动加购已经实现。现有运行版本及测试命令见 AGENTS.md，旧路径验证证据保留在 docs/validation.md：

```text
topps-auto-bot/
  AGENTS.md                   # 本项目规则与实际验证入口
  README.md                   # 只放免责声明
  .gitignore
  pyproject.toml              # 包入口与测试配置
  requirements.txt            # 经验证、可复现的运行依赖
  requirements-dev.txt        # 测试与打包依赖
  config.example.json         # 空白模板，不含真实资料
  src/topps_auto_bot/
    __init__.py
    __main__.py               # 程序入口与单实例锁
    ui.py                    # Tkinter 主线程、设置/任务/驱动面板
    settings.py              # 校验、路径、本地保存与配置版本
    driver_setup.py          # Chrome 检测、驱动下载/导入/验证
    browser.py               # 浏览器会话、可信来源及页面适配
    purchase.py              # 商品/数量核对、单次加购、官方结算和单次购买提交
    runner.py                # 持续库存等待、可证失败重试、取消及分段时序
  tests/unit/

```

不预建插件基类或未来手机适配目录。只有出现实际职责重叠或文件过大时才再拆分。UI 不持有付款决策；浏览器工作线程不直接修改 Tk 控件，通过队列把状态交给主线程。浏览器正常执行官网自身请求，不另建复刻其内部协议的下单客户端。

### 3. User configuration and local data

Windows 程序目录与数据目录分离：安装到当前用户的应用目录，运行数据放 `%LOCALAPPDATA%\ToppsAutoBot\`。macOS 开发使用 `~/Library/Application Support/ToppsAutoBot/`，开发测试允许显式指定临时数据目录，禁止测试读取真实配置。

| 数据 | 内容与处理 |
| --- | --- |
| `config.json` | `schema_version`、单账号登录资料、精确预设库、本次唯一目标、数量/美元限额、收货/信用卡资料、驱动/兼容启动设置；旧窗口和定时时间仅兼容保留，不限制/调度新任务 |
| `browser-profile/` | 专用 Chrome 登录状态，不使用用户日常 Chrome 配置 |
| `drivers/` | 已验证驱动及版本元数据；下载中间文件不视为可用驱动 |
| `driver-staging/` | 每次下载或手动选择的私有暂存副本；与已启用驱动分离，任何未验证或未完成启用的副本不得用于购买 |
| `run-state.json` | 当前任务标识、唯一目标、流程类型、各步骤时间、加购尝试序号/在途及结果、脱敏金额/配送快照、购买提交与结果核对记录；不包含登录凭据、验证码、卡资料、地址、Cookie、令牌或带会话参数的结算 URL |
| `logs/` | 必要的脱敏状态与错误分类，不写原始配置、付款表单、请求正文或支付截图 |

用户明确选择本地明文配置存储，界面需如实说明这一点，不能声称已加密。信用卡资料保持本地配置；已有登录账号/密码可兼容保留且与收货邮箱分开，但首版默认人工登录，缺少这些字段不阻止保存购买资料或启动试用；密码、卡号与 CVV 默认遮蔽，可由用户主动查看、编辑或清除。验证码不持久化；凭据只能用于已核实的官方认证页面，不能上传到无关服务。配置与会话的保护依赖当前 OS 用户目录权限，并不等于抵御同账户恶意程序。

首启没有配置时显示设置表单，不自动开始交易。保存前校验所有字段；钱以十进制字符串存储并用 Decimal 比较，不采用浮点近似。数量为正整数、限额为正且至多两位小数，拒绝重复的商品/规格目标。保存到同目录临时文件，写完并刷新后替换；失败保留旧配置并清理临时文件。

配送策略固定为“沿用网站明确选中的默认项”。本次自动加购核对成功并进入结算，地址和完整报价确认后首次冻结服务及运费。不得重建快照接受变化；该快照只属于本次任务，不写回预设，也不沿用到以后任务。

从准备开始即锁定本次浏览器会话、目标、浏览器启动与交易设置，直到任务完全结束，使用不可变的配置快照。可以保存多个预设，但本次只能选择一个；不自动换目标或将其他预设加入本单。配置格式变化只支持明确的迁移步骤；未知版本或损坏文件提示修复，禁止以默认配置覆盖后继续付款。当前配置为 v2，仅新增登录资料字段，并提供 v1→v2 的明确迁移；不预建更多迁移框架。

安装包显式收集程序资源和空模板，不打包整个工作目录。Git 忽略规则不能替代打包白名单；如果开发中误将真实 `config.json` 加入跟踪，必须取消跟踪并处理泄露问题，不能只补忽略规则。示例资料由本项目自行编写为占位值，不复制参考项目样例。更新保留用户数据；卸载默认保留，提供明确、主动选择的清除配置/会话选项。

### 4. 先复现完整下单流程再评价

业务顺序以参考项目和已有页面观察为依据，交付实际页面定位与多 iframe 支付处理，不只提供 mock 接口。开发者不必先完成真实登录或付款；用户运行到具体步骤时核对页面状态，失败显示步骤及可操作原因。受控页面结果不能推断限量发售胜率。抽签和拍卖不纳入本流程。实际页面访问受限时记录阻塞，不将内部接口重放作为替代。

| 阶段 | 对齐的操作 | 保留的改良 |
| --- | --- | --- |
| 浏览器访问 | UC、持久化专用 profile 与参考启动配置，先访问真实官网 | 版本动态匹配、参数差异可核实、沙箱默认开启；访问结果运行时展示 |
| 操作入口 | 直链或关键词、规格/数量、开始/停止、状态日志 | 搜索结果由用户指定一个，预设是可选复用，不逐项付款 |
| 登录 | 保留专用会话，默认由用户在官网人工完成 | 无需保存登录邮箱/密码，观察登录态后继续，自动登录非前置 |
| 库存 | 同一指定商品未售/售罄时持续观察，直到可购或停止 | 每次读取有限超时，明确异常结束；取消整单60秒截止 |
| 加购 | 选定规格及完整数量，点击后确认购物车；可证明暂时失败再试 | 每次尝试独立记录，仅一个在途；未知/部分成功不重发 |
| 结算付款 | 从购物车进入官方结算，填地址和信用卡并提交 | 默认配送和金额核对，最终购买至多一次，确认实际结果 |

首版默认人工登录：工具先打开专用 UC 浏览器，不依赖完整信用卡配置或 developer verified 标记；用户在官网完成登录和验证码，再点击开始/完成登录让程序检查可观察会话。可获取账号摘要时展示并在本任务中固定；不强制预配置邮箱与网页邮箱精确相等才能试用。固定等十秒或仅点“已完成”不是成功证据，无法确认登录态时提示该具体步骤；已进入购买后会话丢失仍停止而非自动补跑。

已有自动登录模块和可选凭据可保留兼容，不在启动时默默提交，也不作为首版必需测试入口；首版没有登录密码也须能运行人工路径。缺失可选登录字段的旧配置保留交易数据和未决记录，不强制用户补齐。人工等待保留明确状态、停止入口和已有 10 分钟期限，超时结束该任务但可重新开始。

取消全局 DEFAULT_TOPPs_PROFILE.verified 和“必须先实站验收通过”的启动/页面读取闸门。环境正常、用户必要资料和目标有效时允许尝试流程；来源和字段规则随应用提供，依据参考/公开页面及支持的支付服务资料维护，不能用空名单或仅 data-* 测试占位代表交付。各步实际来源或字段不符时暂停/报错，不自动输入卡资料，也不把未知来源一概放行。实际页面变化通过软件更新修正；不要求用户先证明真实付款才启用程序。

搜索/直链确认只形成一个本次目标，不要求额外建立命名预设。用户明确开始后自动完成环境、登录、未决及空车准备，再访问目标商品。RUN_READY 只表示可开始商品流程；未售不要求预先加车，未公布的价格不能猜测，真正加购前仍须核对身份、数量及当前 USD 单价。

取消整单 60 秒与 1–600 秒硬截止，移除剩余提交时间和截止倒计时。正常读取为售罄时等待约 15 秒，入口暂不可用或可重试暂拒时约 10 秒再观察；尊重官方更长等待/排队，不重叠，等待可及时停止。读取异常连续三次仍失败则报告并停止；正常售罄读取会清除该异常计数，不把等货时间长当成错误。超价、身份变化、会话失效、永久拒绝等明确异常停止。

时间约束按步骤分别设置：普通导航/读取/填写初始 30 秒；加购结果从该次动作发出起独立核对最多 30 秒；最终付款结果及银行验证从购买提交起共用 10 分钟；人工登录或无在途购买动作的其他人工挑战等待 10 分钟；已有加购/付款在途时不得因挑战延长其结果期限。库存持续等待可超过 60/600 秒，不能自动套用某次步骤的超时。加购尚在自身核对期限内且任务有效时，确认成功即可进入结算；已停止或已转未决后迟到结果只作核对，不恢复旧任务。

旧 window_seconds、planned_start、deadline 字段仅兼容保留，不限制或自动触发新任务；它们过期也不能解除旧未决记录。UI 显示当前阶段、运行时间、最近库存/尝试结果和停止原因，不生成整单截止。定时、预准备加速和旧 500ms 指标仍留后续效果评价，不作为当前门槛。

### 5. 单任务执行与可核实停止

一个 OS 用户数据目录仅允许一个应用持有执行锁，一个应用只允许一个执行线程。使用独立任务标识和取消事件；开始准备时冻结配置，未收回旧线程和会话控制权前不启用下一任务。

状态主线为 `IDLE → PREPARING/AUTO_LOGIN/AWAITING_MANUAL_LOGIN → RUN_READY → OPENING_PRODUCT/WAITING_AVAILABILITY → ADDING_TO_CART → VERIFYING_CART → CHECKING_OUT → SUBMITTING → AWAITING_VERIFICATION → SUCCEEDED/FAILED/UNKNOWN`，另有 `STOPPING/STOPPED/EXPIRED/UNSUPPORTED`。本人验证仅在官网实际需要时进入。旧 `CART_READY/CHECKOUT_READY` 不是新基线入口；不接续手工准备的车跳过自动加购测试。

每次有副作用的浏览器动作前检查取消和当前步骤是否仍有效；不再检查整单截止。停止立即更新 UI，等待中的 WebDriver 操作按有限超时退出，不把仍在执行的线程标成已停止。停止保留浏览器及实际购物车，不能自动清空；付款提交后停止不代表撤单。会话丢失停止，不能导入日常浏览器 Cookie 或新建会话补跑。

### 6. 加购尝试、JS 兜底与单次付款

使用随程序维护的官网及支付来源规则，在当前页面/每个iframe填写前精确匹配；未知来源暂停，不以“缺少实站验收记录”为由全局阻断。加购前和重试前均复核同一当前会话、精确商品/规格、完整数量、当前 USD 单价及空车。已有车、不明结果、超价或身份异常不自动清理/修复。

每次加购尝试分配独立序号，在操作前保存在途记录；记录失败不点击，写入后再次检查取消。一次仅有一个在途尝试。加购响应明确成功且购物车恰好匹配目标时直接结算，不再加购。部分数量、多余条目或错误规格停止，不补量或删车重试。

只有动作可证明未发出，或官网明确暂时拒绝且可证明没有副作用、没有在途并核实空车，才能先保存该次“未加购”结论，再等待并重查全部条件后新建尝试。永久拒绝停止。单次空车、按钮再次可点、提示消失或点击抛异常不足以证明未发生；这种不明结果及损坏记录仍跨重启阻断，人工核实后只能开始新的空车任务。结论保存失败也不能发起下一次尝试，未决记录不能被新序号覆盖。

JS 兜底按副作用区分：经核实无购买承诺的普通控件点击、滚动、字段填值及事件派发可以使用并回读确认，不强制启用禁用按钮。加购普通点击异常先核对结果；只有符合上述未加购证据条件才允许间隔后以已验证方式（可含 JS）新尝试，不能盲目补点。最终付款须在尝试前选择一种已验证方式，普通点击异常后不得再 JS 点击，反之亦然。

支付表单适配同时支持页面字段和多个独立 iframe。按卡号、持卡人、有效期、CVV 的真实字段容器定位，逐帧解析实际来源、切入填写并核对值/校验状态（敏感字段只验证状态不记录内容），每次用 finally 返回 default_content；DOM/iframe 重建时重新定位当前有效容器，不把资料写入父页面同名框。普通字段填写可以进行已核实的 JS 赋值/事件兜底并回读；缺字段、来源异常、填写失败或状态无法核实必须阻止最终提交。最终付款仍只执行一次，银行验证用户接管，结果不明不重发。

受控集成页面必须把卡字段放进不同iframe，至少覆盖不同 localhost 端口模拟跨源、延迟加载/重建、缺失字段、不允许的来源以及银行验证返回。不能把四个卡字段都放父页面、用空 iframe 占位便宣称支付适配完成。实际站点 selector 不限于测试属性，需按参考流程和公开页面形态实现并具有清楚错误提示。

本次成功加购后进入结算，完整地址/清单/报价确定时固定唯一默认配送身份及最终 USD 运费。无唯一默认、费用未知、币种异常或后续服务/运费变化即停。提交前核对唯一商品、完整数量、单价、配送、税费和最终整单上限。

最终购买前持久化 SUBMITTING，记录目标、实际时间、配送/金额而不含凭据/卡/验证码/地址或签名 URL；记录失败不点，保存后再次检查取消及当前步骤有效性。每个任务最终购买至多一次；能证明未发出则结束该提交尝试，无法确认则保留未决，不自动重提。结果依据本次订单标识与支付状态，不凭固定等待报成功；本人验证后只核对。

旧流程的未决付款与加购仍须识别，字段版本不明或记录损坏保留并阻断；不能因取消整单截止、修改浏览器或引入新重试而清除状态。

### 7. UC 驱动准备与安装流程

安装器复制应用后启动 Tkinter 初始化向导，后续也可从设置页进入。软件可以完成安装但保持“环境未就绪”；任何交易开始都要求初始化已验证。这样不用在安装器中维护另一套下载 UI。

向导先发现 Chrome 路径、版本和系统架构；未找到时引导官网下载 Chrome 或选择已有浏览器路径，不静默安装另一个浏览器。驱动来源使用 Chrome for Testing 官方版本元数据和 HTTPS 下载地址，按 Chrome 构建版本选择兼容版本，禁止写死主版本 146。

自动下载与手动导入统一为“私有暂存区检查 → 完整验证 → 原子启用”：

1. 自动模式分块下载并在私有 `driver-staging/<操作标识>/` 中解压，拒绝路径穿越；手动模式把用户选定的 `chromedriver.exe` 复制到同类暂存区，不修改源文件。暂存副本不是已安装或已启用驱动，运行任务不能发现或使用它。
2. 对同一份暂存副本完成 UC 所需处理，再检查版本和架构，以实际 UC/最终参数启动并关闭独立空白测试浏览器。文件已复制、版本号匹配或某一步成功都不能单独表示验证完成。
3. 全部验证通过且操作仍有效时，将该已验证副本晋升到 `drivers/` 的独立版本位置；最后完整保存有效驱动的路径、版本和模式，将配置选择的原子替换作为启用提交点。文件晋升成功但配置尚未提交时，该文件仍不是当前有效驱动。
4. 提交成功后才显示已启用；之前一直保留旧有效驱动及配置。验证、晋升或配置保存失败均不得覆盖旧选择；新候选失败不代表旧驱动必定失效，旧驱动仍需通过当前 Chrome 兼容性检查才能继续使用。

取消在启用提交前生效时，撤销该操作的启用权限、关闭下载连接并回收工作线程，清理暂存内容，迟到结果不能晋升或修改有效配置。若启用已经提交则显示已完成而非虚报取消，用户可主动重新更换驱动。手动验证成功后使用受管理副本，不再依赖原 Downloads 文件；手动模式遇到不兼容只提示重新选择或主动切换自动下载。

仅在明确下载/切换操作时改变驱动；运行时显式传入已启用并通过 UC 验证的路径，不触发 Selenium Manager 或 UC 的隐式下载/替换。若 UC 会再次修改活动文件或联网，必须先修正暂存/启动集成并重新验证，不能把未验证副本用于购买。

Chrome 更新后开始任务前重新核验匹配关系；下载及空白兼容验证不加载真实账户/付款配置。独立的官网访问诊断在其后执行，可不填凭据即打开首页/商品页；403 表示实站未通过，不等于驱动安装失败，也不能反复重装掩盖。官方版本匹配流程见 [ChromeDriver 文档](https://developer.chrome.com/docs/chromedriver/downloads/version-selection)，手动路径与自动管理边界见 [Selenium Manager 文档](https://www.selenium.dev/documentation/selenium_manager/)。

### 8. 可试用交付验收

- 开发完成要求实际流程实现、代表性受控测试、Windows 安装/升级及使用说明。无需开发者用真实账号登录或真实信用卡扣款；用户实测可选，不作为归档或启动门槛。
- 验证默认人工登录、不填登录邮箱/密码、全局 verified=False 或历史无实站证据都不提前封锁任务。用户启动后，具体来源/字段/预算/未决检查仍正常生效，缺失时显示可处理的错误。
- 修复并回归已发现的代码缺口：先空后部分数量不能保存为 NOT_SENT；结算报价和提交按钮等待有 30 秒期限；加购及付款结果从动作发出起算，不在调用返回后重置；跨 iframe 填卡及恢复上下文真实可执行。
- 保留 UC、持续库存等待、可证失败重试、数量预算、配送和付款单次验证。真实页面式 iframe/登录/搜索形态必须在本地浏览器覆盖，不以“没有实站账号”为由留空实现。
- Windows 验收使用合成资料和受控页面，完成安装、启动、驱动准备、人工登录流程、覆盖升级与数据保留。官网页面访问、实际登录和支付尝试单独记录，不能说成已经成功。

### 9. 用户主动检查更新与覆盖安装

关于/设置显示当前版本和检查更新入口。用户点击后读取发布者随包配置的固定 HTTPS 发布源，展示新版、发行说明及可信下载入口；同版/旧版、超时、断网或非法响应均明确显示，不将查询失败当已最新，不读取账号/卡/profile。发布源不由任意用户输入；开发版未配置时显示未配置，面向用户的发布版需有有效固定入口。

下载通过默认浏览器打开可信发布页或安装包链接，用户运行新版安装器覆盖安装，不要求先卸载或手改 JSON。没有后台常驻服务、不静默自动安装、不做运行中的 exe 自替换。安装器检测应用和任务已结束；若无法正常停止退出，提示处理并拒绝覆盖，不强杀可能在加购/付款的进程。

升级完整保留配置、专用 profile、受管理驱动、加购尝试历史及付款未决；未决不妨碍安全停止后升级，但升级不得解锁或重跑交易。配置迁移只替换已验证结果，失败保留旧资料及可恢复版本；回退遇未知格式停止交易而非覆盖。新版本重检驱动/浏览器兼容，不无故重下。受控更新响应与 Windows 旧版→新版演练覆盖发现新版、失败、取消、数据保留和未知版本，不要求进行真实购买。

## Risks / Trade-offs

- [本地明文卡资料] → 遵循用户决定保存在当前用户目录；默认遮蔽界面、限制文件权限、禁止日志与分发泄露，明确本地保存不等于加密。不擅自换成强制凭据库或仅内存模式。
- [第三方网页与支付变化] → 选择器和可信来源集中管理，验证明确失败就停止；使用脱敏样本及现场记录，不根据旧代码假定字段有效。
- [UC/启动配置也可能仍被拦截] → 在用户尝试时记录真实访问结果，记录版本、参数、profile 和页面结果；不承诺 UC 或某参数必定通过 Cloudflare，挑战交用户，仍失败时明确报告。
- [客户端无法保证第三方支付幂等] → 单次点击、持久化未决状态与官方订单人工核对共同防止自动重复提交。
- [Windows 打包在 Mac 上未验收] → 用 Windows x64 构建和实测；Mac 单元测试不作为安装验收替代。
- [功能参考被误当成可移植源码] → 不引入、复制或逐句翻译参考仓库的源码、注释、文档与资源，从当前功能规格和实际网站行为独立编写。语言变化本身不作为免除授权问题的依据，也不作零版权风险保证。实际使用的第三方库、安装器和其他资源仍按其许可处理；参考 [GitHub 许可说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository) 与 [软件思想及表达的区分](https://ipc.court.gov.cn/zh-cn/news/view-407.html)。
- [加购可能成功但客户端未确认] → 加购前记录在途，异常后不重发或自动修车，人工核实后重新从空车任务开始。旧购物车/结算页起点的测试没有覆盖这一风险。
- [基线与抢购效果不同] → 普通在售商品用于完整流程验证，限量竞争表现待后续实际场次；不把基线成功解释为抢购已优化。
- [平台自动购买规则] → 正常浏览器会话本身不代表平台允许自动化。官网条款列有对 bots/scripts/自动购买工具的限制；现场使用需核对允许范围，验证码由用户处理，兼容结果按实测记录，不能承诺该工具必然可长期运行。见 [Topps 条款](https://www.topps.com/pages/terms-of-use)。
- [持续等待与操作卡死不同] → 正常库存等待持续到可购/停止；单步、人工等待和连续读取错误仍有界，界面可取消。取消旧整单截止不等于所有请求无超时。

## Migration Plan

1. 本轮仅改规范与任务，保留现有实现和历史记录。默认人工登录、移除全局启动闸门、多iframe支付、审查缺陷及更新能力分别列为待办；不能仅因209项旧测试通过把缺口勾掉。
2. 先使无登录密码的用户能打开浏览器并人工登录开始；随包实现参考流程页面规则，在步骤失败时提示，不留全局假开关或空名单。
3. 补多iframe支付、失败/来源处理和真实风格受控测试，修复重试阻断与超时回归；不执行真实购买，不以真实成交作为继续开发的必要输入。
4. 完成检查更新及覆盖安装，构建并在 Windows 合成环境验收；维护设置/使用/安装/升级说明。缺 Windows 环境或发布地址时如实列出待验证/待配置项，不伪称完成。
5. 实现、受控测试与Windows交付要求完成后可按用户指示归档；可选真实试用未做不阻止归档，也不得被记录为已通过。
